# Phase 2: Registration Data Persistence

## Purpose

This phase moved the project from a neutral foundation into a concrete user-facing feature: storing a new user account in MySQL through a plain Java backend.

The goal was to implement the registration flow without introducing frameworks or authentication. The work was limited to:

- a browser form for new user registration
- a Java HTTP endpoint for receiving form submissions
- validation on the server side
- password hashing before persistence
- a MySQL table for user data
- JDBC-based database insertion

## Fixed Constraints

The project remained within the original architecture:

- HTML + CSS + Vanilla JavaScript for the frontend
- Java for backend logic
- JDBC for database access
- MySQL for persistence
- Gradle for build and execution
- no frameworks, no ORM, no auth system

This phase intentionally did not add login, sessions, JWT, cookies, Spring, or any other application framework.

## System Overview

The registration feature follows a simple flow:

1. The browser loads a registration form from the static resources.
2. The user fills in name, phone number, email, and password.
3. JavaScript submits a POST request to `/api/register`.
4. The Java `HttpServer` receives the request.
5. The form payload is parsed into a `RegistrationRequest`.
6. The backend validates the fields.
7. The password is hashed with PBKDF2.
8. The data is inserted into the MySQL `users` table.
9. A response is returned to the browser with success or validation errors.

## Previous Foundation Used in This Phase

This phase depends on the earlier boilerplate work:

- Java 21 toolchain already configured
- Gradle project structure already present
- JDBC connection setup using environment variables
- backend entrypoint using `HttpServer`
- static frontend resources served from `src/main/resources/static`

## Request and Validation Flow

The registration request is represented as a Java record and validated in `RegistrationService`.

The required checks are:

- name must not be blank
- phone number must not be blank
- email must not be blank
- email must match a basic format check
- password must not be blank
- duplicate email is rejected

The validation logic is intentionally server-side. The browser may also do lightweight client-side checks, but the Java layer is the source of truth.

## Password Handling

Passwords are never stored in plain text.

The project uses PBKDF2 with HMAC-SHA256 through Java's crypto APIs. The hash is generated before inserting the user and stored in the database as a single string value.

The generated value follows the format:

```text
pbkdf2-sha256$600000$salt$hash
```

This is a secure, non-plaintext representation suitable for later password verification in future authentication work.

## Database Schema

The persistence layer uses a MySQL table named `users`.

```sql
CREATE TABLE IF NOT EXISTS users (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    phone_number VARCHAR(32) NOT NULL,
    email VARCHAR(254) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_email (email)
);
```

Important aspects:

- `email` is unique, preventing duplicate registrations
- `password_hash` stores the hashed value
- `id` is autogenerated by MySQL
- `name` and `phone_number` are stored as plain strings for the current feature scope

## Java Backend Components

### `app.Application`

This is the main entrypoint. It:

- reads `PORT` from the environment with a default of `8080`
- creates a `RegistrationService` using `DatabaseConfig.fromEnvironment()`
- starts a JDK `HttpServer`
- exposes `/` for static HTML and CSS/JS assets
- exposes `/api/register` for registration operations

### `DatabaseConfig`

This class reads the required environment variables:

- `DB_URL`
- `DB_USERNAME`
- `DB_PASSWORD`

It fails early with an exception if any required variable is missing.

### `JdbcConnectionFactory`

This factory creates a JDBC `Connection` by calling `DriverManager.getConnection(...)` with the configured DB credentials.

### `RegistrationService`

This is the core registration logic. It:

- calls validation helpers
- hashes the password
- opens a JDBC connection
- executes an `INSERT INTO users ... VALUES (?, ?, ?, ?)` statement
- returns the generated user ID
- catches `SQLIntegrityConstraintViolationException` and converts it into a duplicate-email-specific error

### `DuplicateEmailException`

A domain-specific exception used to signal that a registration attempt repeated an existing email address.

## Frontend Interaction

The frontend is served as static files:

- `src/main/resources/static/index.html`
- `src/main/resources/static/styles.css`
- `src/main/resources/static/app.js`

The form posts data using `fetch` to `/api/register` with URL-encoded form fields.

The JavaScript handles:

- successful registration
- validation error responses
- duplicate email responses
- form reset on success

## HTTP API Behavior

The backend registration endpoint accepts a form-encoded POST request.

Examples of response codes:

- `201 Created` for a successful registration
- `400 Bad Request` for invalid input
- `409 Conflict` for duplicate email
- `500 Internal Server Error` for unexpected server-side failures

This keeps the API explicit and easy to test with curl or browser dev tools.

## Why This Phase Matters

This phase creates the first real end-to-end business feature: a user can submit their details and have the data persisted.

It establishes the pattern the application will use for future flows:

- request parsing
- validation
- persistence
- error mapping
- response generation

It also confirms the basic architecture is sound: static frontend + Java service layer + JDBC + MySQL.

## Important Note

This phase is about data persistence and registration logic, not authentication. There is no login flow, no session management, and no authorized-user system yet.

The project is deliberately preparing the persistence layer and account creation flow so that authentication can be added later in a clean, separate phase.

## Verification Goal

This phase is considered complete when the following are true:

- the project builds successfully
- the server starts with valid environment variables
- the registration endpoint accepts a valid payload
- the user is inserted into MySQL
- duplicate emails are rejected
- invalid input is rejected
- the password hash is stored rather than a plaintext password
